# Аналіз рефакторингу та дотримання принципів ООП

В рамках лабораторної роботи №1a було проведено рефакторинг ігрового рушія 2D Zombie Survival Game. Початковий код мав високу зв'язність (tight coupling) між класами логіки та обробки подій. Для покращення архітектури (Object-Oriented Design) було впроваджено патерни **Factory Method** та **Observer**.

## 1. Застосовані патерни проєктування (GoF)
* **Factory Method (Фабричний метод):** Створено клас `EnemyFactory`, який інкапсулює логіку ініціалізації ворогів (`Zombie`, `Boss`). Тепер головний клас гри не знає про внутрішні характеристики ворогів (здоров'я, шкода, лють), а лише передає координати для спавну.
* **Observer (Спостерігач):** Реалізовано інтерфейс `IObserver` та конкретний клас `ScoreManager`. Сутності ворогів тепер є "видавцями" (Publishers) подій смерті. Коли здоров'я ворога падає до нуля, він викликає `notifyObserversOnDeath()`, і `ScoreManager` автоматично нараховує очки. Це розірвало жорстку залежність між ігровими сутностями та системою підрахунку прогресу гравця.

## 2. Дотримання принципів SOLID
* **S - Single Responsibility Principle (Принцип єдиної відповідальності):** Клас `Game` був розвантажений. Тепер він відповідає виключно за Game Loop, `EnemyFactory` — за створення об'єктів, а `ScoreManager` — за управління рахунком.
* **O - Open/Closed Principle (Принцип відкритості/закритості):** Завдяки патерну Observer, система відкрита для розширення. Якщо в майбутньому знадобиться додати систему досягнень (Achievements) або звукових ефектів при вбивстві, достатньо буде створити новий клас, що реалізує `IObserver`, і додати його до списку слухачів ворога. Модифікувати код самого ворога не доведеться.

## 3. Загальні принципи проєктування
* **DRY (Don't Repeat Yourself):** Усунуто дублювання коду при нарахуванні очок. Тепер логіка підрахунку винагороди зосереджена у перевизначених методах `notifyObserversOnDeath()` (10 очок для Zombie, 50 очок для Boss).
* **KISS (Keep It Simple, Stupid):** Спрощено інтерфейс створення ворогів. Виклик `make_unique<Boss>("BOSS", 120, 20, bossX, bossY, 7)` замінено на інтуїтивно зрозумілий `enemyFactory.createBossEntity(bossX, bossY)`.
* **Відмова від антипатернів:** З усіх заголовкових файлів (`.h`) було прибрано глобальні оголошення `using namespace std;`, що відповідає стандартам безпечного програмування на C++ та запобігає конфліктам просторів імен.

## 4. Порівняння продуктивності
Обсяг коду дещо зріс через додавання нових класів та інтерфейсів (IObserver, ScoreManager, EnemyFactory), проте показник **Coupling** (залежності) значно зменшився. Продуктивність Game Loop (FPS) залишилася на стабільно високому рівні, оскільки патерни генерації подій (Observer) працюють за час O(N), де N — кількість слухачів (у нашому випадку 1), що є вкрай ефективним.
