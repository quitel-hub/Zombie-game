# Звіт з лабораторної роботи №1a
**Тема:** Аналіз, UML-моделювання та рефакторинг існуючої програмної системи.
**Проєкт:** 2D Zombie Survival Game (C++, SFML).

## 1. Мета роботи
Побудувати UML-моделі для існуючого коду ігрового рушія. Проаналізувати архітектуру на предмет порушень принципів об'єктно-орієнтованого дизайну. Запропонувати та реалізувати архітектурні зміни з використанням патернів проєктування (GoF) для покращення розширюваності та зменшення зв'язності (coupling).

## 2. Моделювання початкового стану (UML)

До проведення рефакторингу було побудовано три базові діаграми:

1. **Діаграма варіантів використання (Use Case Diagram):** Відображає основні дії Гравця (Player) у системі: переміщення персонажа, атака ворогів, отримання шкоди, перемикання зброї та управління станом гри (пауза/вихід).
2. **Діаграма класів (Class Diagram - Initial):**
   Показує початкову структуру, де класи сутностей (`Zombie`, `Boss`, `Player`) містять і логіку, і обробку подій. Головний клас `Game` напряму створює об'єкти та жорстко керує нарахуванням очок, що порушує принцип єдиної відповідальності (SRP).
3. **Діаграма послідовності (Sequence Diagram):**
   Описує життєвий цикл гри (`Game Loop`), який складається з трьох фаз: обробка подій (`pollEvent`), оновлення логіки та фізики (`updateGameState`), і рендеринг графіки (`renderFrame`).

## 3. Проєктування змін та впровадження патернів

Для покращення архітектури було впроваджено два патерни проєктування:

* **Factory Method (Фабричний метод):** Створено клас `EnemyFactory`, який повністю інкапсулює логіку ініціалізації ворогів (`Zombie`, `Boss`). Тепер головному циклу гри не потрібно знати базові характеристики (HP, Damage) — він лише передає координати для спавну.
* **Observer (Спостерігач):** Реалізовано інтерфейс `IObserver` та конкретний клас-слухач `ScoreManager`. Сутності ворогів тепер є "видавцями" (Publishers) подій. Коли здоров'я ворога падає до 0, він викликає метод `notifyObserversOnDeath()`, і `ScoreManager` автоматично нараховує потрібну кількість очок (10 за Zombie, 50 за Boss). 

## 4. Аналіз принципів SOLID та якості коду

* **S (Single Responsibility Principle):** Клас `Game` був розвантажений. Тепер він відповідає виключно за управління станами гри, тоді як створення об'єктів делеговано Фабриці, а підрахунок прогресу — Менеджеру рахунку.
* **O (Open/Closed Principle):** Завдяки патерну Observer система відкрита для розширення. Якщо потрібно додати звуковий ефект при вбивстві боса, достатньо створити нового слухача (`AudioObserver`) і підписати його на події, не змінюючи код самого класу `Boss`.
* **DRY (Don't Repeat Yourself):** Усунуто дублювання коду при нарахуванні очок у методі обробки атак.
* **Стандартизація коду:** З усіх заголовкових файлів (`.h`) видалено антипатерн `using namespace std;`, що запобігає конфліктам імен і робить код безпечнішим. Всі стандартні типи тепер використовують явний простір імен `std::`.

## 5. Висновки
В ході виконання роботи було успішно проаналізовано та рефакторено ігровий C++ рушій. Впровадження патернів Factory Method та Observer дозволило значно знизити зв'язність класів (Coupling) та підвищити читабельність коду. Збірка проєкту налаштована за допомогою CMake, всі проблеми сумісності та кодування були успішно вирішені.
